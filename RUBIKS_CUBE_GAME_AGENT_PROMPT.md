# Prompt: Build a Polished Portable Rubik's Cube Game / Interactive Simulation

You are an implementation agent. Your task is to create a polished, portable Rubik's cube game and interactive simulation from scratch in this workspace. Do not stop at a prototype. Work one step at a time until the app is feature-complete, visually polished, verified through direct interaction, and ready for a user to run locally.

## Goal

Build a portable Rubik's cube simulation that looks and behaves like a real 3x3 Rubik's cube. It must support realistic visible cube rotations, intuitive layer moves, camera/view controls, solvable random scrambles, solved reset, shortcut states such as the daisy and white cross, and a library of common move sequences for novice, intermediate, and expert users.

The final result should be a self-contained local app that can run reliably on the user's machine with clear startup instructions. Prefer a browser-based implementation if no existing project constraints indicate otherwise, because it is naturally portable.

## Non-Negotiable Requirements

1. The cube must look like a real Rubik's cube:
   - Render 27 cubies with visible separation, bevels or rounded edges where practical, colored sticker faces, and realistic lighting.
   - During rotations, the moving slice must rotate as a physical layer, not merely swap colors instantly.
   - Rotations must preserve cube geometry and sticker orientation correctly.
   - The cube should remain visually coherent from all camera angles.

2. Use real Rubik's cube move semantics:
   - Support standard face moves: `U`, `D`, `L`, `R`, `F`, `B`.
   - Support counter-clockwise moves: `U'`, `D'`, `L'`, `R'`, `F'`, `B'`.
   - Support double moves: `U2`, `D2`, `L2`, `R2`, `F2`, `B2`.
   - Consider adding middle-slice moves `M`, `E`, `S`, whole-cube rotations `x`, `y`, `z`, and wide moves if implementation time permits after the required feature set is solid.
   - Use standard Rubik's notation in the UI so users can learn transferable terminology.

3. Controls must include:
   - Buttons or menus for rotating each face/layer clockwise, counter-clockwise, and 180 degrees.
   - Camera/view controls for orbiting, zooming, and resetting the view.
   - Keyboard shortcuts for common moves and camera actions.
   - Reset to solved.
   - Random scramble that is guaranteed reachable and solvable because it is generated by applying legal moves to a solved cube.
   - Jump to a daisy state.
   - Jump to a white cross state.
   - Trigger buttons for common algorithms or combinations used by novice, intermediate, and expert solvers.
   - Undo/redo or move history if feasible; include at least a visible move log.

4. Background and visual polish:
   - Include a subtle cherry tree / floating blossom background.
   - The background should enhance the experience without distracting from the cube or reducing UI readability.
   - Floating or falling blossoms should be lightweight and tasteful.
   - Avoid a toy-looking flat prototype; aim for a finished interactive simulation.

5. Verification is mandatory:
   - Launch the app locally.
   - Use either computer use, browser automation, Playwright, direct browser control, or equivalent direct interaction tooling.
   - Take screenshots at multiple states and viewport sizes.
   - Emulate mouse/keyboard interactions and confirm that controls work.
   - Inspect visual quality repeatedly while implementing.
   - Verify animated slice rotations, sticker/cubie orientation, scramble solvability approach, solved reset, daisy state, white cross state, algorithm buttons, camera controls, and keyboard shortcuts.
   - Do not rely only on code inspection. You must visually and interactively test the running app.

## Suggested Technology Direction

Use a browser app with Three.js unless the existing workspace strongly suggests another stack. Three.js is preferred because it can render a convincing 3D cube, supports camera controls, and is portable.

Recommended baseline:

- Vite or another lightweight local dev server.
- TypeScript if the project setup supports it cleanly; otherwise modern JavaScript is acceptable.
- Three.js for the 3D scene.
- OrbitControls or equivalent for camera orbit/zoom/pan.
- A small, explicit cube-state model that maps cubie positions and orientations to legal moves.
- CSS/HTML controls for the command surface.
- No backend unless there is a compelling reason.

Before choosing dependencies, inspect the workspace. If an existing app/framework is already present, adapt to its conventions instead of replacing it.

## Implementation Plan

Start by expanding this plan based on the actual workspace. Then execute it step by step. Keep progress visible and do not mark the task complete until every required feature is implemented and verified.

### Phase 1: Scout and Decide

1. Inspect the workspace:
   - Existing package files, framework, source layout, build/test scripts, and local instructions.
   - Any repo-specific `AGENTS.md` or equivalent guidance.
   - Existing lint/test/build tooling.

2. Decide the implementation shape:
   - If no app exists, create a portable browser app.
   - If an app exists, integrate into it with minimal disruption.
   - Choose exact libraries and justify the choice briefly in the implementation notes.

3. Define done criteria:
   - Running command.
   - Build command.
   - Verification commands.
   - Screenshots or artifacts proving the important states.

### Phase 2: Core Cube Model

1. Implement an internal 3x3 cube representation:
   - Track cubie identity, position, and face colors/stickers.
   - Support legal face turns with correct state transitions.
   - Support notation parsing for move strings such as `R U R' U'`.
   - Support queues of moves so animations can play sequentially.

2. Implement required state operations:
   - Solved reset.
   - Random scramble by applying a sequence of legal moves to solved state.
   - Daisy preset by applying or constructing a valid state that could occur on a real cube.
   - White cross preset by applying or constructing a valid state that could occur on a real cube.
   - Move log with clear notation.

3. Add algorithm definitions:
   - Novice examples, such as right-hand algorithm `R U R' U'`, left-hand algorithm `L' U' L U`, and basic insertion sequences.
   - Intermediate examples, such as common F2L triggers or OLL/PLL beginner subsets.
   - Expert examples, such as selected PLL or OLL algorithms.
   - Keep labels accurate and avoid overclaiming if an algorithm depends on cube orientation or case setup.

### Phase 3: 3D Rendering and Animation

1. Build the Three.js scene:
   - Camera, lights, renderer, controls, and responsive resize handling.
   - 27 cubies placed in a 3x3x3 grid.
   - Colored sticker faces with conventional colors: white, yellow, red, orange, blue, green.
   - Black or dark plastic cube body/gaps.
   - Rounded edges or bevel effect if feasible without making the implementation brittle.

2. Animate moves:
   - Group the rotating slice temporarily.
   - Rotate it around the correct axis.
   - On completion, snap transforms to exact grid coordinates.
   - Update the logical cube state exactly once per move.
   - Prevent conflicting simultaneous moves or queue them safely.

3. Validate the visual physics:
   - Face/layer rotations must look like a real cube layer turning.
   - Cubies must not drift, clip badly, or lose sticker orientation.
   - Animation speed should feel smooth and responsive.

### Phase 4: Controls and Interaction

1. Build a usable control surface:
   - Face-move controls for `U D L R F B`, including clockwise, counter-clockwise, and 180-degree variants.
   - A scramble button with configurable or sensible move count.
   - Solved reset.
   - Daisy and white cross buttons.
   - Algorithm buttons grouped by novice, intermediate, and expert.
   - Move log and status area.

2. Add keyboard shortcuts:
   - Letter keys for basic face moves.
   - Shift or another modifier for inverse moves.
   - Number or bracket shortcuts for camera/reset/scramble if ergonomic.
   - Display shortcut hints in a compact, non-intrusive way.

3. Add camera/view controls:
   - Orbit with mouse/touch.
   - Zoom.
   - Reset view.
   - Optional preset views: front, top, right, isometric.

4. Make the app responsive:
   - Desktop layout with controls accessible without crowding the cube.
   - Mobile/tablet layout that still allows interaction.
   - No text overlap or clipped controls.

### Phase 5: Cherry Blossom Background and Polish

1. Add a subtle cherry tree / blossom environment:
   - Use lightweight procedural particles, CSS animation, or Three.js sprites.
   - Include a restrained cherry tree silhouette or branch motif.
   - Blossoms should drift/fall slowly and should not obscure cube controls.

2. Polish the final UI:
   - Consistent spacing and typography.
   - Accessible contrast.
   - Clear button states.
   - Controls that are dense enough to be useful but not cluttered.
   - Avoid decorative UI that makes the simulation harder to use.

### Phase 6: Verification Loop

You must run the app and verify it interactively throughout implementation. Use direct browser automation or computer use. Take screenshots and inspect them.

Minimum verification checklist:

1. App launches locally with the documented command.
2. Initial cube appears solved and visually polished.
3. Mouse/touch camera orbit and zoom work.
4. View reset works.
5. Each required face move animates the correct slice:
   - `U`, `D`, `L`, `R`, `F`, `B`.
   - Inverse moves.
   - Double moves.
6. Multiple queued moves execute in order.
7. Scramble generates a legal sequence from solved state and leaves the cube in a plausible scrambled state.
8. Solved reset restores the cube exactly.
9. Daisy button produces a visible daisy configuration.
10. White cross button produces a visible white cross configuration.
11. Algorithm buttons run their sequences in order and update the move log.
12. Keyboard shortcuts trigger the expected moves.
13. The cube still looks real during rotation, not like flat stickers teleporting.
14. Layout works at desktop and mobile viewport sizes.
15. Background blossoms animate subtly and do not obscure the cube or controls.
16. Production build succeeds if the stack has a build step.

When a check fails, fix the implementation and rerun the relevant verification. Do not mark completion with known failures.

## Quality Expectations

- Favor a robust cube-state model over ad hoc visual-only swaps.
- Keep animation and logical state synchronized.
- Use exact snapping after rotations to avoid accumulated floating-point drift.
- Keep UI controls discoverable and accurate.
- Use standard terminology where possible: face turns, inverse moves, double moves, slice moves, whole-cube rotations, algorithms.
- Make the final app feel finished, not like an internal demo.
- Maintain a concise implementation log in the final response with changed files, commands run, verification performed, and any known limitations.
